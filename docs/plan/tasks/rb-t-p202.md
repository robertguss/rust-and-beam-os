# RB-T-P202: Boot a static musl process with correct initial stack, auxv, TLS, and errno

## Goal

Prove the C runtime entry contract before adding files, mappings, and native threads.

## Context

[Architecture & Validation Plan](<../architecture.md>)

Only processes declared with `abi = "linux-aarch64-beam-v1"` may see this compatibility personality. It is an adapter over project-native objects, not the public API for Rust services. Implement only the exact pinned static-musl/ERTS workload contract.

Blocked by: RB-T-P201.

## Deliverables

* Construct the Linux-shaped initial stack with admitted `argc`, `argv`, environment, auxiliary-vector entries, random bytes, page size, program headers, and terminators.
* Support the minimal identity, output, and exit calls required by a static-musl hello program.
* Initialize main-thread TLS and thread-pointer state correctly for musl; prove thread-local `errno` behavior.
* Create tiny static C programs built with the exact target toolchain for startup, arguments, environment, TLS, errno, stdout/stderr, and exit.

## Acceptance criteria

- [ ] Static-musl hello reaches `main`, validates arguments/environment/auxv, writes expected bytes, and exits with the expected status.
- [ ] TLS and `errno` remain process/thread-local and aligned as required.
- [ ] Malformed executable metadata or oversized startup data fails before EL0 entry.
- [ ] No dynamic interpreter, loader, shared object, shell, or host-provided runtime appears in the image.

## Verification

* `just build-musl-probes`
* `just test-musl-startup`

## Evidence

* Run each C probe repeatedly under QEMU.
* Compare startup values with the pinned AArch64 Linux reference where semantics are intended to match.
* Save initial-stack fixtures, ELF inventory, and serial results.

## Out of scope

* General POSIX/Linux compatibility, networking, fork/exec, dynamic linking, writable filesystems, JIT, GUI, and phone hardware.
* Silent approximation of unsupported flags or semantics.
* ERTS source changes; this phase validates the host beneath ERTS.

## Additional context
### Completion rule

Done requires contract-linked positive, negative, boundary, error, and concurrency evidence. Unknown behavior must fail loudly. A rare race is a blocker, not an acceptable flake.
### Learning checkpoint

Explain the relevant Linux/musl contract, the kernel invariant beneath it, the dangerous race or memory-ordering edge, and how the conformance evidence proves the chosen behavior.
### Readiness-audit correction — 2026-08-30

### Exact startup contract

* Build the initial stack from one typed representation and prove the AArch64 ABI alignment, `argc`, ordered `argv`, environment, terminating nulls, auxv terminator, bounded string bytes, and overflow-safe address layout.
* Emit only the auxv entries required by the exact artifact/contract. Reconcile `AT_PHDR`, `AT_PHENT`, `AT_PHNUM`, `AT_PAGESZ`, `AT_ENTRY`, `AT_BASE` if applicable, `AT_RANDOM`, `AT_EXECFN` if observed, `AT_HWCAP`, and `AT_HWCAP2` with RB-T-P014/RB-E-P108; never copy a host auxv wholesale.
* `AT_HWCAP`/`AT_HWCAP2` must reflect state the kernel actually preserves and interfaces it actually implements. In particular FP/ASIMD depends on RB-T-P113, atomics on RB-T-P200, and unimplemented SVE/SME/MTE/GCS bits remain clear.
* Verify the exact static ELF type/relocation/TLS model from RB-T-P005. Reject `PT_INTERP`, dynamic dependencies, unsupported TLS/relocations, malformed program-header metadata, and entry/stack mappings outside the process.
* Initialize TPIDR_EL0/main-thread TLS, stack canary/random-dependent musl state, `errno`, integer registers, FP/SIMD state, mask placeholder, and thread identity with no reused-task data.

### Entropy staging rule

* A named diagnostic profile may use deterministic `AT_RANDOM` bytes only when its seed and bytes are generated by the test harness and the receipt is marked non-production.
* RB-T-P202 can prove stack/TLS mechanics with that profile, but Gate 2 and every ERTS qualification require RB-T-P211B's production entropy path. Production preflight must reject deterministic, zero, repeated, or unavailable startup randomness.

### Required additional evidence

* Byte-exact Linux-reference stack/auxv fixtures where values are intended to match; randomized stack-layout parser tests; truncation/overflow/duplicate/missing-entry corpus; HWCAP negative instruction probes; TLS alignment/guard/canary checks; host-leak scan; and deliberate auxv/platform drift canaries.
