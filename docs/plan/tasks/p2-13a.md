# P2-13a: Freeze the M2 contention campaign, progress oracle, and leak criteria before execution

[Architecture & Validation Plan](<../architecture.md>)

## Goal

Pre-register the exact one-hour M2 qualification method so results cannot be accepted through post-hoc threshold selection, an unsuitable runner, or a graph that merely looks stable.

## What to build

* Select the P0-16-approved runner profile for the full long-stress campaign and separate companion profiles for architecture semantics, deterministic race/fault exploration, and performance. Do not assume Linux/TCG is the full-duration runner.
* Freeze exact QEMU/accelerator/CPU/machine/vCPU/RAM/device/image/build identity, host-resource minimums, host-load policy, disk/artifact budget, watchdogs, interruption policy, and preflight.
* Define campaign duration in both host monotonic wall time and guest monotonic time; state which is authoritative for minimum coverage and how pauses/stalls are detected.
* Freeze the workload mix, operation-rate floor, thread/process/object population, seed schedule, preemption/fault injection schedule, phase order, warm-up, sample cadence, trace mode, and artifact retention before seeing a qualification result.
* Define liveness/progress oracles for each subsystem: scheduler dispatch, thread lifecycle, mutex/condition/futex handoff, timer expiry, signal delivery/return, stream bytes, poll completions, mapping churn, and cleanup.
* Divide resources into exact-conservation classes and bounded-retention classes. Exact classes must return to baseline at declared quiescent checkpoints; retained caches/pools must have a predeclared warm-up, maximum envelope, slope estimator, uncertainty/confidence rule, and absolute cap.
* Define failure categories: guest invariant failure, deadlock/livelock/progress failure, resource/accounting failure, unknown contract event, trace/evidence loss, runner invalidity, host interruption, and harness defect. None may be silently retried into success.
* Freeze pass/fail rules, required replicas/seeds, treatment of censored/interrupted runs, and the exact rerun/replay policy before execution.
* Generate a signed/hashed `m2-qualification-manifest.json` consumed by the runner and final report.

## Acceptance criteria

- [ ] The manifest is complete enough for a fresh agent to execute and judge the campaign without choosing any new threshold.
- [ ] Every original M2 invariant maps to at least one online assertion, quiescent conservation check, or post-run analysis with a named data field.
- [ ] The selected runner passes capacity/preflight and is explicitly valid for the conclusions drawn; TCG/KVM/HVF evidence classes remain distinct.
- [ ] Workload progress has lower bounds, so a quiet deadlocked or degraded system cannot pass merely because resources stopped changing.
- [ ] Every retained resource has both an absolute cap and a non-growth/plateau rule; every exact resource has a baseline checkpoint.
- [ ] Trace overflow, counter reset/wrap, missing sample, clock anomaly, artifact truncation, or runner drift automatically invalidates the run.
- [ ] Thresholds and manifest hash are committed before the first official result is inspected.

## Required tests and evidence

* Dry-run each phase at reduced duration; deliberately stall each subsystem and prove its progress oracle fails; inject exact-resource leaks and slow retained-resource slopes; truncate traces/samples; drift the runner; interrupt the host; and prove classification is deterministic.
* Have an independent fresh session review the manifest without implementation context.

## Verification commands

* `just build-m2-qualification-manifest`
* `just validate-m2-qualification-manifest`
* `just dry-run-m2-qualification`
* `just test-m2-oracles`

## Out of scope

* Changing implementation to meet a desired graph, selecting thresholds after results, claiming TCG performance represents KVM/HVF, or substituting a shorter run without a gate decision.

## Completion rule

Done means the runner, workload, duration, progress floors, resource rules, failure taxonomy, artifacts, and pass/fail decision procedure are frozen before the official campaign begins.

## Learning checkpoint

Explain how the campaign distinguishes leak, bounded caching, deadlock, livelock, under-load degradation, runner failure, and missing evidence without inspecting source code.
