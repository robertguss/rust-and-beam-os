# P0-15: Prove the no_std Slint renderer path and freeze the toolkit/license decision

[Architecture & Validation Plan](<../architecture.md>)

## Goal

Prove the proposed UI toolkit can actually compile and render within the POC's `no_std`, process-isolated, software-rendered constraints—and make the license decision before the architecture is frozen.

## Why this is a blocker

The existing Gate 0 claims the toolkit and license are frozen, but the first implementation proof was deferred to M5. Slint's `unsafe-single-threaded` no-std feature intentionally disregards normal `Send`/`Sync` safety and requires that exactly one thread call the Slint API. Its royalty-free license does not cover embedded products; an open-source embedded POC uses the GPLv3 path unless a paid license is chosen.

## What to build

* Pin an exact Slint release and minimal feature set with default features disabled.
* Compile an ahead-of-time `.slint` component for the project's native AArch64 renderer target without shipping the Slint compiler in the image.
* Implement a probe-only custom `Platform`/software-renderer adapter over the Phase 0 framebuffer/input/time interfaces.
* Render a deterministic component with embedded font/assets on both TCG and HVF; process one pointer action and one timer-driven redraw.
* Measure binary size, static/data/heap/stack high-water memory, redraw cost, frame cadence, and dependency closure.
* Define and test a single-owner renderer-thread rule: only the renderer event-loop thread may call Slint APIs; device/IPC producers communicate through bounded queues or wakeups.
* Produce a license ADR choosing GPLv3-compatible open-source distribution, a paid Slint license, or a replacement toolkit. Describe combined-work distribution implications rather than assuming process isolation changes the license.
* Identify a toolkit-neutral `UiBackend` seam and a minimal mock/alternate renderer so the kernel ABI and Rust↔BEAM protocol do not depend on Slint types.

## Acceptance criteria

- [ ] The exact pinned component builds for the intended `no_std` AArch64 userspace target from a sealed toolchain.
- [ ] The component renders and accepts pointer/timer input through the Phase 0 guest path on TCG and HVF.
- [ ] All calls into Slint are proven to occur on one renderer thread; a test or runtime assertion rejects cross-thread calls.
- [ ] No unbounded allocation, unsupported system API, hidden dynamic library, host renderer, or runtime compiler participates.
- [ ] Measured memory and frame behavior fit the provisional renderer budget or force an explicit replacement/narrowing decision.
- [ ] The user has an explicit, technically and legally accurate license choice before GATE-0.
- [ ] If Slint fails any blocking criterion, the issue selects and proves a replacement before P5 UI work is considered ready.

## Required tests and evidence

* Sealed `no_std` cross-build and dependency-feature audit.
* TCG/HVF render, input, timer, queue-wakeup, and forced cross-thread negative tests.
* Binary/memory/frame measurements with exact build provenance.
* SPDX/license inventory and reviewed toolkit ADR.

## Verification commands

* `just build-slint-probe`
* `just run-slint-probe-tcg`
* `just run-slint-probe-hvf`
* `just audit-slint-features`
* `just license-check`

## Out of scope

* Building the final Runtime Lab UI, GPU acceleration, multiple UI threads, accessibility, mobile widgets, or dynamic UI code from BEAM.
* Treating process isolation as a substitute for complying with the selected license.

## Completion rule

Done means the exact toolkit/version/features, memory feasibility, single-thread safety contract, replacement seam, and distribution license are proven and frozen before kernel implementation is authorized.

## Learning checkpoint

Explain the Slint custom-platform path, software rendering, why `unsafe-single-threaded` is a real safety obligation, and why the license decision belongs in Phase 0.
