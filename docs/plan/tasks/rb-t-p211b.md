# RB-T-P211B: Implement boot entropy, virtio RNG, AT_RANDOM, and bounded getrandom semantics

## Goal

Provide an explicit, testable entropy path for the initial auxiliary vector and any admitted musl/ERTS random requests, without silently treating a reproducible test seed as production entropy.

## Context

Blocked by: RB-T-P201, RB-T-P205A, RB-T-P014.

## Deliverables

* Add the selected QEMU virtio RNG device/transport to the frozen machine manifest and discover it through the approved DTB/PCI path.
* Implement the minimal kernel virtio-rng driver or reuse the pinned audited crate path with explicit queue, DMA, interrupt/polling, reset, timeout, bounds, and error semantics.
* Define boot entropy readiness: when the first production process may receive `AT_RANDOM`, what happens if the device is absent/stalled, and whether boot fails rather than supplying predictable bytes.
* Populate the exact required `AT_RANDOM` byte count for each process launch from a consumed/recorded entropy request, with no buffer reuse or cross-process disclosure.
* Implement only the observed `getrandom`/random-read flags and partial-read behavior; reject unsupported modes. Bound request size and kernel buffering.
* Provide a clearly named deterministic test mode whose seed and generated bytes are stored in evidence. Production/qualification manifests must cryptographically or structurally exclude that mode.
* Record device identity/features, request/response lengths, timeout/failure counters, and mode without logging random payloads.
* Add continuous/freshness sanity checks suitable for catching a dead or repeating virtual device, while explicitly avoiding a claim of cryptographic certification.

## Acceptance criteria

- [ ] Production-profile boot cannot reach EL0 with deterministic, zero, reused, or unavailable `AT_RANDOM` bytes.
- [ ] Test mode is fully reproducible and visibly marked in every receipt; production and qualification preflight reject it.
- [ ] Separate processes and repeated boots receive distinct bytes in the production profile, with no payload exposure in ordinary traces.
- [ ] Admitted random calls handle partial results, interruption, invalid flags/pointers/lengths, device stall/reset, and resource exhaustion according to the frozen contract.
- [ ] DMA/queue bounds and device-generation handling prevent stale completion, overwrite, or access outside owned buffers.
- [ ] Missing or failed entropy has one explicit fail-closed outcome and never falls back silently.

## Verification

* `just test-rng-driver`
* `just test-at-random`
* `just stress-getrandom`
* `just verify-production-entropy-mode`

## Evidence

* Deterministic-mode golden sequence; production distinctness/freshness sanity campaign; device absent/stall/reset/short-completion/DMA-bound fault injection; concurrent request stress; cross-process disclosure canary; manifest/preflight tests that reject deterministic production.

## Out of scope

* Cryptographic certification, entropy estimation claims, hardware TRNG support, persistent entropy pools, `/dev/random` compatibility, networking-based seeding, or physical phone hardware.

## Additional context
### Completion rule

Done means startup/random consumers receive bounded data from an explicit production source, deterministic mode is confined to test evidence, and failure is never silently predictable.
